5 分钟动手实现第一个 LLM 智能体
#

智能体入门实践笔记：用几十行 Python 代码，从零搭建一个能“思考”、能“调用工具”的旅行助手。

这篇笔记要解决什么问题？
#

前面学过智能体的任务环境、核心运行机制以及 Thought-Action-Observation 交互范式。但理论只有配合动手实践，理解才会更扎实。

本篇目标是：从零开始构建一个可以工作的智能旅行助手。它会严格遵循理论中的循环：

  1. 接收用户请求；
  2. 由 LLM 进行思考（Thought）；
  3. 决定并执行行动（Action）；
  4. 获取观察结果（Observation）；
  5. 回到第 2 步，直到任务完成。

要解决的用户任务定义为：

你好，请帮我查询一下今天北京的天气，然后根据天气推荐一个合适的旅游景点。

这个任务看起来简单，但它要求智能体展现出清晰的逻辑规划能力：

  • 先调用天气查询工具；
  • 把天气结果作为下一步的依据；
  • 再调用景点推荐工具；
  • 最后合成一段完整的建议。

读完这篇笔记，你应该能理解：

  • 一个最简智能体需要哪些组件；
  • 提示工程如何驱动 LLM 做决策；
  • 工具函数是怎么被解析和调用的；
  • 主循环如何把 Thought-Action-Observation 串起来。

先理清概念：智能体、LLM、工具是什么关系？
#

动手前先区分几个容易混淆的词，后面看代码会更清楚。

概念 通俗理解
LLM 大脑，负责理解和推理，但只能输出文本，无法直接动手
工具 Tool 手和眼睛，比如查天气、搜索网页、执行代码、查数据库
智能体 Agent 把大脑和工具组合起来、能自主完成多步任务的系统
智能体循环 让“思考 → 行动 → 观察”反复迭代的调度过程

一个关键认知：LLM 本身不是智能体。LLM 只是智能体里的“决策核心”。真正让它变成智能体的，是外面那层“循环 + 工具 + 记忆”。

这也解释了为什么同样一个模型，直接聊天时它只能说“我无法联网”，而放进智能体后却能查到实时天气——区别不在模型，而在有没有给它接上工具和循环。

ReAct：Thought-Action-Observation 的来源
#

这种“边思考边行动”的范式有一个名字：ReAct（Reasoning + Acting）。它的核心思想是：

让模型把推理过程（Thought）和外部行动（Action）交替进行，并把每次行动的结果（Observation）反馈给下一轮推理。

一个完整步骤可以写成：

Thought: 我需要先知道天气
Action: get_weather(city="北京")
Observation: 北京当前天气:Sunny，气温26摄氏度

对比两种极端做法，能看出 ReAct 的价值：

方式 做法 问题
只推理 让模型一次性想完所有步骤再回答 没有外部信息，容易“幻觉”
只调用 模型不解释，直接决定调哪个工具 决策过程不可见，难调试
ReAct 推理和行动交替进行 既用上外部信息，又保留可读的思考过程

我们这篇笔记实现的，正是 ReAct 的最简版本。

智能体的最小骨架
#

在动手之前，先把整个系统的结构画清楚：

                ┌──────────────────────────────┐
用户请求 ─────▶ │  主循环 (Agent Loop)          │
                │                              │
                │   构建 Prompt                │
                │       │                      │
                │       ▼                      │
                │   调用 LLM                   │ ◀── system_prompt
                │       │                      │      (指令模板)
                │       ▼                      │
                │   解析 Thought / Action      │
                │       │                      │
                │       ├── 调用工具 ──┐        │
                │       │              ▼        │
                │       │        工具函数执行   │
                │       │              │        │
                │       │              ▼        │
                │       │        Observation   │
                │       │              │        │
                │       └── Finish ───▶ 输出答案 │
                └──────────────────────────────┘

一句话概括：主循环负责调度，LLM 负责思考，工具负责和真实世界交互。

准备工作：安装依赖
#

为了从 Python 程序中访问网络 API，我们需要几个库。这里使用 uv 来安装，它比传统 pip 更快，也更适合管理大模型相关依赖。

uv pip install requests tavily-python openai

如果还没有 uv，可以先安装它：

pip install uv
依赖 作用
requests Python 中最流行的 HTTP 库，用于调用网络接口
tavily-python AI 搜索 API 客户端，用于获取实时网络搜索结果
openai OpenAI 官方 Python SDK，用于调用兼容 OpenAI 接口的 LLM

组件一：指令模板（system_prompt）
#

驱动 LLM 的关键在于提示工程（Prompt Engineering）。我们需要设计一个“指令模板”，告诉 LLM：

  • 它扮演什么角色；
  • 它拥有哪些工具；
  • 它应该如何格式化思考和行动。

这个模板就是智能体的“说明书”，会作为 system_prompt 传给 LLM。

AGENT_SYSTEM_PROMPT = """
你是一个智能旅行助手。你的任务是分析用户的请求，并使用可用工具一步步地解决问题。

# 可用工具:
- `get_weather(city: str)`: 查询指定城市的实时天气。
- `get_attraction(city: str, weather: str)`: 根据城市和天气搜索推荐的旅游景点。

# 输出格式要求:
你的每次回复必须严格遵循以下格式，包含一对 Thought 和 Action：

Thought: [你的思考过程和下一步计划]
Action: [你要执行的具体行动]

Action 的格式必须是以下之一：
1. 调用工具：function_name(arg_name="arg_value")
2. 结束任务：Finish[最终答案]

# 重要提示:
- 每次只输出一对 Thought-Action
- Action 必须在同一行，不要换行
- 当收集到足够信息可以回答用户问题时，必须使用 Action: Finish[最终答案] 结束

请开始吧！
"""

这里有一个关键设计：约束输出格式。

我们不是让模型“自由发挥”，而是要求它按固定结构输出 Thought 和 Action。这样主循环才能稳定解析。这是从“聊天机器人”走向“智能体”的第一步：让模型的输出变成可被程序理解的指令。

一个好的 system_prompt 通常包含四部分
#

部分 作用 本例对应
角色定义 告诉模型它是谁 “你是一个智能旅行助手”
工具说明 告诉模型有哪些能力可用 “可用工具”列表
输出格式 约束模型的回复结构 Thought / Action 格式要求
行为规则 约束模型的行为边界 “每次只输出一对”“必须用 Finish 结束”

写 system_prompt 时，一个实用原则是：像给一个新同事写操作手册一样写。要明确、具体、有示例，而不是含糊地交代任务。

几个让 Prompt 更稳定的技巧
#

  1. 用固定关键词标记结构：比如 Thought:、Action:、Finish[]，方便正则解析。
  2. 给出动作的两种形态：调用工具 / 结束任务，覆盖所有合法路径。
  3. 显式禁止常见错误：例如“不要换行”“每次只输出一对”，能显著降低解析失败率。
  4. 保留示例：复杂任务里，给一两个 Few-shot 示例比长篇描述更有效。

组件二：工具函数
#

智能体和真实世界交互的方式就是工具。这里实现两个工具。

工具 1：查询真实天气
#

使用免费的天气查询服务 wttr.in，它能以 JSON 格式返回指定城市的天气数据。

import requests


def get_weather(city: str) -> str:
    """
    通过调用 wttr.in API 查询真实的天气信息。
    """
    url = f"https://wttr.in/{city}?format=j1"

    try:
        response = requests.get(url)
        response.raise_for_status()
        data = response.json()

        current_condition = data["current_condition"][0]
        weather_desc = current_condition["weatherDesc"][0]["value"]
        temp_c = current_condition["temp_C"]

        return f"{city}当前天气:{weather_desc}，气温{temp_c}摄氏度"

    except requests.exceptions.RequestException as e:
        return f"错误:查询天气时遇到网络问题 - {e}"
    except (KeyError, IndexError) as e:
        return f"错误:解析天气数据失败，可能是城市名称无效 - {e}"

几点说明：

细节 作用
format=j1 让接口返回 JSON，而不是纯文本
raise_for_status() 状态码非 200 时主动抛异常
两层 try / except 分别处理网络错误和数据解析错误

注意函数返回的是自然语言字符串，而不是原始 JSON。这是因为它的返回值会直接拼回 Prompt，作为 Observation 喂给 LLM。返回越干净，LLM 越容易理解。

工具 2：搜索并推荐景点
#

定义一个 get_attraction，根据城市和天气在互联网上搜索合适的景点。

import os
from tavily import TavilyClient


def get_attraction(city: str, weather: str) -> str:
    """
    根据城市和天气，使用 Tavily Search API 搜索并返回景点推荐。
    """
    api_key = os.environ.get("TAVILY_API_KEY")
    if not api_key:
        return "错误:未配置 TAVILY_API_KEY 环境变量。"

    tavily = TavilyClient(api_key=api_key)
    query = f"'{city}' 在'{weather}'天气下最值得去的旅游景点推荐及理由"

    try:
        response = tavily.search(
            query=query,
            search_depth="basic",
            include_answer=True,
        )

        if response.get("answer"):
            return response["answer"]

        formatted_results = []
        for result in response.get("results", []):
            formatted_results.append(f"- {result['title']}: {result['content']}")

        if not formatted_results:
            return "抱歉，没有找到相关的旅游景点推荐。"

        return "根据搜索，为您找到以下信息:\n" + "\n".join(formatted_results)

    except Exception as e:
        return f"错误:执行 Tavily 搜索时出现问题 - {e}"

这里有一个值得注意的设计：include_answer=True。它会返回一个基于所有搜索结果的综合回答 response["answer"]，这比直接拼接一堆网页摘要更干净，也更符合 LLM 阅读习惯。

工具注册
#

把所有工具函数放入一个字典，方便主循环按名字调用：

available_tools = {
    "get_weather": get_weather,
    "get_attraction": get_attraction,
}

这种“工具名 → 函数”的映射，是智能体框架里非常通用的模式。后续要扩展能力，只需要往这个字典里加新函数，再更新 system_prompt 里的工具说明即可。

组件三：接入大语言模型
#

当前很多 LLM 服务商（OpenAI、Azure，以及 Ollama、vLLM 等开源模型服务框架）都遵循与 OpenAI API 相似的接口规范。这种标准化为开发者带来极大便利。

我们实现一个通用客户端 OpenAICompatibleClient，它可以连接任何兼容 OpenAI 接口的 LLM 服务。

from openai import OpenAI


class OpenAICompatibleClient:
    """
    一个用于调用任何兼容 OpenAI 接口的 LLM 服务的客户端。
    """

    def __init__(self, model: str, api_key: str, base_url: str):
        self.model = model
        self.client = OpenAI(api_key=api_key, base_url=base_url)

    def generate(self, prompt: str, system_prompt: str) -> str:
        """调用 LLM API 来生成回应。"""
        print("正在调用大语言模型...")
        try:
            messages = [
                {"role": "system", "content": system_prompt},
                {"role": "user", "content": prompt},
            ]
            response = self.client.chat.completions.create(
                model=self.model,
                messages=messages,
                stream=False,
            )
            answer = response.choices[0].message.content
            print("大语言模型响应成功。")
            return answer
        except Exception as e:
            print(f"调用 LLM API 时发生错误: {e}")
            return "错误:调用语言模型服务时出错。"

实例化时需要三个信息：

参数 含义
api_key LLM 服务的 API Key
base_url LLM 服务地址，OpenAI 官方、Azure、Ollama、vLLM 都可以
model 具体模型 ID

这正是不久前我在 AMD ROCm 上用 vLLM 部署 Gemma 4 之后，可以复用的接口形态：本地 vLLM 服务天然兼容 OpenAI 接口，可以直接作为这里的 base_url。

组件四：执行行动循环
#

下面这个主循环把所有组件整合起来，通过格式化后的 Prompt 驱动 LLM 决策。

import re
import os

# --- 1. 配置 LLM 客户端 ---
API_KEY = "YOUR_API_KEY"
BASE_URL = "YOUR_BASE_URL"
MODEL_ID = "YOUR_MODEL_ID"
os.environ["TAVILY_API_KEY"] = "YOUR_TAVILY_API_KEY"

llm = OpenAICompatibleClient(model=MODEL_ID, api_key=API_KEY, base_url=BASE_URL)

# --- 2. 初始化 ---
user_prompt = "你好，请帮我查询一下今天北京的天气，然后根据天气推荐一个合适的旅游景点。"
prompt_history = [f"用户请求: {user_prompt}"]

print(f"用户输入: {user_prompt}\n" + "=" * 40)

# --- 3. 运行主循环 ---
for i in range(5):  # 设置最大循环次数
    print(f"--- 循环 {i + 1} ---\n")

    # 3.1 构建 Prompt
    full_prompt = "\n".join(prompt_history)

    # 3.2 调用 LLM 进行思考
    llm_output = llm.generate(full_prompt, system_prompt=AGENT_SYSTEM_PROMPT)

    # 模型可能会输出多余的 Thought-Action，需要截断
    match = re.search(
        r"(Thought:.*?Action:.*?)(?=\n\s*(?:Thought:|Action:|Observation:)|\Z)",
        llm_output,
        re.DOTALL,
    )
    if match:
        truncated = match.group(1).strip()
        if truncated != llm_output.strip():
            llm_output = truncated
            print("已截断多余的 Thought-Action 对")

    print(f"模型输出:\n{llm_output}\n")
    prompt_history.append(llm_output)

    # 3.3 解析并执行行动
    action_match = re.search(r"Action: (.*)", llm_output, re.DOTALL)
    if not action_match:
        observation = "错误: 未能解析到 Action 字段。请确保你的回复严格遵循 'Thought: ... Action: ...' 的格式。"
        observation_str = f"Observation: {observation}"
        print(f"{observation_str}\n" + "=" * 40)
        prompt_history.append(observation_str)
        continue

    action_str = action_match.group(1).strip()

    # 结束任务
    if action_str.startswith("Finish"):
        final_answer = re.match(r"Finish\[(.*)\]", action_str).group(1)
        print(f"任务完成，最终答案: {final_answer}")
        break

    # 调用工具
    tool_name = re.search(r"(\w+)\(", action_str).group(1)
    args_str = re.search(r"\((.*)\)", action_str).group(1)
    kwargs = dict(re.findall(r'(\w+)="([^"]*)"', args_str))

    if tool_name in available_tools:
        observation = available_tools[tool_name](**kwargs)
    else:
        observation = f"错误:未定义的工具 '{tool_name}'"

    # 3.4 记录观察结果
    observation_str = f"Observation: {observation}"
    print(f"{observation_str}\n" + "=" * 40)
    prompt_history.append(observation_str)

主循环里的四个关键动作
#

这个循环看起来长，但其实只有四件事：

动作 说明
构建 Prompt 把历史拼接成完整上下文，让 LLM 知道之前发生了什么
调用 LLM 让模型输出 Thought + Action
解析 Action 用正则把模型输出拆成“工具名 + 参数”，或识别 Finish
执行并记录 调用工具，把 Observation 追加进历史

为什么是“历史拼接”而不是“多轮 messages”？
#

这里用 prompt_history 把所有内容拼成一段长文本，而不是用 OpenAI 的多轮 messages。原因是：Observation 不是模型生成的内容，而是工具返回的结果。把它以 Observation: ... 的形式拼进同一份上下文，能让 LLM 更稳定地按 Thought-Action-Observation 结构继续推理。

Prompt 历史是如何一步步膨胀的？
#

理解智能体的关键，之一就是看清楚上下文是怎么“长大”的。以这个任务为例，prompt_history 的演化大致如下：

第 0 步（初始）:
  用户请求: 查询北京天气并推荐景点

第 1 步（追加 LLM 输出）:
  Thought: 先获取天气
  Action: get_weather(city="北京")

第 2 步（追加 Observation）:
  Observation: 北京当前天气:Sunny，气温26摄氏度

第 3 步（追加 LLM 输出）:
  Thought: 已知天气晴朗，推荐景点
  Action: get_attraction(city="北京", weather="Sunny")

第 4 步（追加 Observation）:
  Observation: 推荐颐和园、长城……

第 5 步（追加 LLM 输出）:
  Thought: 信息充足，可以回答
  Action: Finish[最终答案]

可以看到，每一轮都把“模型输出”和“工具返回”追加进历史。LLM 看到的，是一条不断变长的、完整的推理链。

这也带来一个工程问题：随着循环次数增加，Prompt 会越来越长。所以前面主循环里设置了 for i in range(5) 作为最大循环次数，这是一种最基本的“防爆”措施。

几处容易踩坑的正则
#

正则 作用
Action: (.*) 提取 Action 行内容
Finish\[(.*)\] 提取最终答案
(\w+)\( 提取工具函数名
\((.*)\) 提取参数部分
(\w+)="([^"]*)" 提取键值对参数

正则是这种“纯文本协议”智能体最容易出错的地方。这也是为什么后来主流框架（LangChain、LlamaIndex）会改用更结构化的 function calling，而不是靠正则解析自然语言。

运行案例：一个完整的三轮循环
#

下面是一个成功的执行流程。

用户输入: 你好，请帮我查询一下今天北京的天气，然后根据天气推荐一个合适的旅游景点。
========================================
--- 循环 1 ---

正在调用大语言模型...
大语言模型响应成功。
模型输出:
Thought: 首先需要获取北京今天的天气情况，之后再根据天气情况来推荐旅游景点。
Action: get_weather(city="北京")

Observation: 北京当前天气:Sunny，气温26摄氏度
========================================
--- 循环 2 ---

正在调用大语言模型...
大语言模型响应成功。
模型输出:
Thought: 已经知道北京今天天气晴朗且温度适中，接下来可以基于这个信息推荐一个适合的旅游景点。
Action: get_attraction(city="北京", weather="Sunny")

Observation: 北京在晴天最值得去的旅游景点是颐和园，因其美丽的湖景和古建筑。另一个推荐是长城，因其壮观的景观和历史意义。
========================================
--- 循环 3 ---

正在调用大语言模型...
大语言模型响应成功。
模型输出:
Thought: 已经获得了两个适合晴天游览的景点建议，现在可以根据这些信息给用户提供满意的答复。
Action: Finish[今天北京的天气是晴朗的，气温26摄氏度，非常适合外出游玩。我推荐您去颐和园欣赏美丽的湖景和古建筑，或者前往长城体验其壮观的景观和深厚的历史意义。希望您有一个愉快的旅行！]

任务完成，最终答案: 今天北京的天气是晴朗的，气温26摄氏度，非常适合外出游玩。我推荐您去颐和园欣赏美丽的湖景和古建筑，或者前往长城体验其壮观的景观和深厚的历史意义。希望您有一个愉快的旅行！

三轮循环分别体现了什么能力
#

循环 Action 体现的能力
第 1 轮 get_weather 任务分解：先做依赖项（查天气）
第 2 轮 get_attraction 上下文理解：把上一轮 Observation 当作输入
第 3 轮 Finish 结果合成：把天气 + 景点整合成完整回答

这正好对应智能体的四项基本能力：任务分解、工具调用、上下文理解、结果合成。

纯文本协议 vs 原生 Function Calling
#

本篇用的是“纯文本协议”：靠 system_prompt 约束格式，靠正则解析。这是最容易理解、也最贴近 ReAct 原始论文的方式。

但现在主流 LLM（OpenAI、Claude、通义、DeepSeek 等）大多支持原生 Function Calling / Tool Use。两种方式对比：

维度 纯文本协议（本篇） 原生 Function Calling
实现难度 低，几行正则即可 中，需要按规范定义工具 schema
解析稳定性 依赖模型遵循格式，偶尔会失败 模型直接返回结构化结果，更稳定
思考可见性 Thought 显式可见，过程透明 思考过程被封装，调试相对不直观
兼容性 几乎所有模型都能用 需要模型/服务商支持
适合场景 教学、理解原理、轻量任务 生产环境、复杂工具编排

我的建议是：学习阶段用纯文本协议理解原理，生产环境用 Function Calling 提升稳定性。两者并不冲突，理解了前者，再用后者时会非常顺手。

这个最简智能体有哪些局限？
#

跑通之后，更容易看出它的边界。这个例子虽然能工作，但还有不少可以改进的地方：

局限 说明 改进方向
依赖正则解析 模型格式稍微变一下就可能解析失败 改用原生 function calling
单线程串行 工具只能一个一个执行 引入并行工具调用
无记忆 每次任务独立，不记住历史 加入会话记忆 / 向量记忆
无错误恢复 工具失败只能把错误塞回 Prompt 增加重试和兜底策略
Prompt 容易膨胀 历史越拼越长，token 成本上升 做摘要或限制历史长度
缺少安全控制 没有限制模型能做什么 加入工具权限和审计

理解这些局限，也就理解了为什么需要 LangChain、LlamaIndex、AutoGen 这类框架：它们把上面这些问题抽象成了更通用的组件。

学习心得
#

1. 智能体的核心是“循环 + 工具”
#

理解了 Thought-Action-Observation 循环，再看任何智能体框架都不会觉得神秘。它们的复杂度主要在于：如何更稳地解析 Action、如何更聪明地调度工具、如何管理越来越长的上下文。

2. 提示工程决定了智能体的“性格”
#

同样一套工具，system_prompt 不同，智能体表现可以差很多。写得清楚、约束严格，模型就更稳定；写得模糊，模型就容易“自由发挥”，导致解析失败。

3. 工具是智能体和真实世界的接口
#

天气、搜索、数据库、代码执行……本质上都是“函数”。智能体的能力上限，很多时候不取决于模型本身，而取决于你能给它接上多少可靠的工具。

4. 从零实现一次，胜过读十遍框架文档
#

亲手写过正则解析、亲手拼过 Prompt 历史，再用 LangChain 时，才会真正理解它每个抽象在解决什么问题。

下一步可以做什么？
#

跑通这个最简版本后，可以尝试逐步演进：

方向 具体做法
替换解析方式 用 OpenAI function calling 替代正则
接入本地模型 用之前在 ROCm 上 vLLM 部署的 Gemma 4 作为 LLM
增加记忆 用向量数据库保存历史会话
多工具编排 加入计算、代码执行、数据库查询等工具
引入规划 在 Action 前增加 Plan 步骤，先拆解再执行
框架对比 用 LangChain / LlamaIndex 重写一遍，对比差异

总结
#

这篇笔记用几十行 Python 代码，实现了一个能“思考”、能“调用工具”的智能旅行助手。整个过程可以浓缩成：

system_prompt 约束输出格式
→ 工具函数封装真实能力
→ LLM 负责 Thought 决策
→ 主循环解析 Action 并执行
→ Observation 回灌上下文
→ 循环直到 Finish

这个案例集中演示了基于 Thought-Action-Observation 范式的智能体所具备的核心能力：任务分解、工具调用、上下文理解和结果合成。正是通过这个循环的不断迭代，智能体才得以把一个模糊的用户意图，转化为一系列具体、可执行的步骤，并最终达成目标。

理解了这个最小闭环，再去学习更复杂的智能体框架，就会有清晰的参照系。
