在 AMD ROCm 云环境用 LoRA 微调 Gemma 4 情感分类模型
#

Datawhale × AMD 开发者活动实践记录。

本次任务目标：在 AMD ROCm 云环境中，使用 LoRA 将通用的 Gemma 4 E4B-it 模型微调成一个能够识别 6 类情绪的文本分类模型。

写在前面
#

继上一篇在 AMD ROCm 云平台上部署 Gemma 4 之后，这次实践继续往前走一步：不只是让模型“跑起来”，而是让模型“学会一个具体任务”。

官方 Notebook 给出了一条比较完整的微调链路：准备环境、加载数据集、格式化样本、配置 LoRA、训练 Adapter、评估微调前后效果。整体流程非常适合初学者理解大模型微调的基本范式。

不过在真实的 ROCm 云环境中，我还是遇到了一些依赖冲突和版本兼容问题。本文会重点记录：

  • AMD ROCm 环境下的硬件与显存情况；
  • LoRA 微调 Gemma 4 的核心流程；
  • torchaudio、transformers、数据集加载等几个排错点；
  • 微调前后指标变化；
  • 对 LoRA、ROCm 生态和大模型训练的理解。

这篇文章更像是一份“实践笔记 + 避坑指南”，希望能帮助同样准备在 AMD 平台上尝试大模型微调的朋友少走一些弯路。

任务概览
#

本次实验的目标是：把一个通用指令模型微调成情感分类助手。

项目 内容
基座模型 Gemma 4 E4B-it
训练方式 LoRA / PEFT
任务类型 文本情感分类
输出类别 6 类情绪标签
运行环境 AMD ROCm 云 GPU 环境
主要框架 PyTorch、Transformers、PEFT、TRL、Datasets
评估指标 Accuracy、Macro F1、Invalid Prediction

这类任务非常适合作为第一次微调练习，因为它有几个优点：

  1. 任务边界清晰：输入一句文本，输出一个情绪标签。
  2. 评估方式明确：可以直接计算准确率和 F1。
  3. 输出格式可控：模型只需要输出固定类别，而不是长文本生成。
  4. 微调收益直观：微调前后效果差异很容易观察。

实验环境与复现清单
#

为了后续复盘，我把这次实验涉及的关键环境整理成一张表。大模型训练里，环境信息非常重要，因为同样的代码在不同 PyTorch、Transformers 或 ROCm 版本下可能表现完全不同。

检查项 作用
amd-smi 确认 AMD GPU 是否被系统识别，查看显存和进程占用
python --version 确认 Python 版本，避免过新或过旧导致依赖不兼容
pip show torch 查看当前 PyTorch 版本及安装来源
pip show transformers peft trl 确认微调相关库版本
torch.cuda.is_available() 在 PyTorch 中确认 ROCm GPU 是否可用
torch.cuda.is_bf16_supported() 确认是否可以使用 bf16 训练

建议在 Notebook 开头保留一个环境检查 Cell：

import torch
import transformers
import peft
import trl

print("torch:", torch.__version__)
print("transformers:", transformers.__version__)
print("peft:", peft.__version__)
print("trl:", trl.__version__)
print("gpu available:", torch.cuda.is_available())
print("device:", torch.cuda.get_device_name(0) if torch.cuda.is_available() else "N/A")
print("bf16 supported:", torch.cuda.is_bf16_supported() if torch.cuda.is_available() else False)

如果后面遇到问题，这些版本信息就是最重要的排查线索。

硬件初探：48GB 显存带来的底气
#

在开始训练前，先查看云环境中的 GPU 信息。

amd-smi

本次分配到的 AMD GPU 显存约为 48GB。对于 Gemma 4 E4B 这类 4B 量级模型的 LoRA 微调来说，这个显存空间非常充裕。

还可以用 PyTorch 检查 GPU 和 bf16 支持情况：

import torch

print("ROCm available:", torch.cuda.is_available())
print("Device:", torch.cuda.get_device_name(0))
print("bf16 supported:", torch.cuda.is_bf16_supported())

这里有一个容易让新手困惑的点：在 ROCm 环境中，PyTorch 依然使用 torch.cuda 这一套接口。也就是说，代码里出现 cuda 并不代表你一定在使用 NVIDIA GPU，它更多是 PyTorch 对 GPU 设备的统一抽象。

为什么 48GB 显存很重要？
#

大模型训练最容易卡住的资源就是显存。显存不仅要存模型权重，还要存：

  • 前向传播的中间激活；
  • 梯度；
  • 优化器状态；
  • LoRA Adapter 参数；
  • batch 中的 token 数据；
  • 训练框架额外缓存。

LoRA 已经大幅降低了训练成本，但显存仍然会决定你能否使用更大的 batch size、更长的上下文和更高精度的数据类型。

本次实验中，因为显存比较充裕，可以直接使用 bf16 训练，而不必一开始就引入 4bit / 8bit 量化。这对于第一次理解微调流程来说会更简单，也能减少量化相关依赖带来的额外复杂度。

训练时也可以开一个终端持续观察显存变化：

watch -n 1 amd-smi

我建议重点看两个阶段：

  1. 模型刚加载时：显存会快速上升，这是权重和运行缓存进入 GPU 的过程。
  2. 训练开始后：显存会继续增加，因为反向传播需要保存激活、梯度和优化器相关状态。

这能帮助我们建立一个直观认识：部署只需要推理资源，而训练需要额外保存大量中间状态，所以训练的显存压力通常比推理更大。

微调前先理解：LoRA 到底做了什么？
#

如果把大模型看成一个已经训练好的“通才员工”，那么微调就是让它熟悉某个岗位的工作规范。

全量微调会更新模型中的大量参数，训练成本高，显存压力也大。LoRA 的思路则更轻量：

冻结原始模型参数，只在部分线性层旁边插入可训练的低秩矩阵，让模型通过这些小参数学习新任务。

它的优点很适合个人开发者和教学实验：

  • 需要训练的参数量少；
  • 显存占用更低；
  • 训练速度更快；
  • 产出的 Adapter 文件体积小；
  • 可以保留同一个基座模型，按任务切换不同 Adapter。

这也是为什么本次任务选择 LoRA，而不是直接全量微调 Gemma 4。

可以把 LoRA Adapter 理解成一个“外挂技能包”：

基座模型 Gemma 4：保留通用语言能力
LoRA Adapter：学习情感分类这个具体任务
最终效果：通用能力 + 任务习惯

这也带来一个很实用的好处：同一个基座模型可以挂载不同 Adapter。例如一个 Adapter 做情感分类，另一个 Adapter 做摘要风格控制，再另一个 Adapter 做领域问答。这样不用为每个任务都保存一整份大模型。

排错实录：ROCm 环境下的依赖连环坑
#

官方 Notebook 的整体逻辑很顺，但在真实云环境中，依赖版本仍然是最容易出问题的地方。下面是我这次遇到的几个典型问题。

坑 1：torchaudio 与 ROCm 环境冲突
#

报错现象
#

在导入 transformers 或执行训练相关代码时，出现类似错误：

AttributeError: partially initialized module 'torchaudio' has no attribute 'lib'

或者出现 undefined symbol 一类底层动态库错误。

原因分析
#

transformers 在某些路径下会尝试导入音频相关模块，而环境中的 torchaudio 可能并不是针对当前 ROCm / PyTorch 版本编译的。结果就是导入 C++ 扩展时失败，并进一步导致 transformers 初始化异常。

但本次任务是纯文本情绪分类，并不需要音频处理能力。因此，最简单直接的处理方式就是卸载 torchaudio。

解决方案
#

在 Notebook 开头或终端中执行：

pip uninstall torchaudio -y

如果是在 Jupyter Notebook 中执行，卸载后建议重启 Kernel。否则 Python 进程中可能仍然残留已经导入失败的模块状态。

坑 2：transformers 大版本升级导致接口不兼容
#

报错现象
#

卸载 torchaudio 后，又遇到类似问题：

ModuleNotFoundError: Could not import module 'BloomPreTrainedModel'

或者某些训练工具中找不到 set_seed、模型类、loss 相关模块。

原因分析
#

问题通常来自依赖被升级到了不兼容的大版本。比如直接执行：

pip install -U transformers

可能会把 transformers 升级到较新的大版本，而当前的 peft、trl、vllm 或 Notebook 代码仍然依赖 transformers 4.x 的接口。大版本变更会带来 breaking changes，进而导致连锁报错。

解决思路
#

更稳妥的方式是锁定一组兼容依赖，而不是无脑升级到最新版本。示例：

uv pip install vllm modelscope transformers accelerate datasets trl peft \
  scikit-learn pandas tqdm torchvision \
  --no-cache \
  -i https://mirrors.cloud.tencent.com/pypi/simple/ \
  --extra-index-url https://wheels.vllm.ai/rocm/

如果已经出现版本冲突，可以先查看当前版本：

pip show transformers peft trl accelerate torch torchvision

再根据 Notebook 或官方环境说明调整版本。我的经验是：在 ROCm 环境里，依赖版本“能稳定跑通”比“追最新”更重要。

坑 3：ModelScope 数据集加载的版本错配
#

报错现象
#

使用 ModelScope 的 MsDataset.load() 加载数据集时，可能出现：

as_dataset() got an unexpected keyword argument 'verification_mode'

原因分析
#

这是典型的数据集工具链版本错配问题。ModelScope、datasets、pyarrow 等库之间存在接口差异，某些参数在不同版本中并不完全兼容。

解决方案
#

我最终采用的方式是：先把数据集仓库下载到本地，再用 Hugging Face datasets 从本地 parquet 文件加载。

思路如下：

from modelscope.hub.snapshot_download import snapshot_download
from datasets import load_dataset

local_dir = snapshot_download("your-dataset-repo")
dataset = load_dataset("parquet", data_files={
    "train": f"{local_dir}/train*.parquet",
    "validation": f"{local_dir}/validation*.parquet",
})

如果标签列需要恢复成分类类型，可以再配合 cast_column 和 ClassLabel 显式指定类别。

这样做的好处是：

  • 绕开 MsDataset.load() 的兼容问题；
  • 本地 parquet 文件可重复读取；
  • 数据处理逻辑更接近 Hugging Face 生态；
  • 后续训练、评估和切分更可控。

核心流程：把通用模型改造成情感分类助手
#

解决环境问题后，微调流程就清晰很多。整体可以拆成五步：

加载数据 → 格式化 Prompt → 配置 LoRA → 训练 Adapter → 评估效果

1. 数据格式化：让模型学会固定输出
#

原始数据通常是这样的结构：

text:  i feel a little sad today
label: sadness

为了适配 Gemma 4 的 Chat 模板，需要把它改造成对话格式。示意如下：

<bos><|turn>system
You are an emotion classification assistant.
Classify the user's text into one of the following labels:
anger, fear, joy, love, sadness, surprise.<turn|>
<|turn>user
Classify the emotion of this text:
i feel a little sad today<turn|>
<|turn>model
sadness

这一步非常关键。我们不是让模型“自由发挥”，而是在训练它形成一种条件反射：

看到一段文本，只输出一个情绪标签，不解释，不扩写。

这也是为什么微调后无效输出会明显减少。模型不只是学到了分类能力，也学到了输出格式。

6 类情绪标签
#

本次任务使用的标签空间可以整理如下：

标签 含义 示例语义
anger 愤怒 生气、不满、抱怨、被冒犯
fear 恐惧 害怕、担忧、焦虑、不安
joy 快乐 开心、满足、兴奋、积极
love 爱 / 喜爱 喜欢、亲密、感激、温柔情绪
sadness 悲伤 难过、失落、沮丧、孤独
surprise 惊讶 意外、震惊、没想到

固定标签空间的好处是评估非常明确。只要模型输出不在这 6 个标签里，就可以直接记为无效预测，而不是靠人工主观判断。

2. LoRA 配置：只训练少量 Adapter 参数
#

本次 Notebook 使用的 LoRA 配置大致如下：

from peft import LoraConfig

lora_config = LoraConfig(
    r=16,
    lora_alpha=32,
    target_modules="all-linear",
    lora_dropout=0.05,
    bias="none",
    task_type="CAUSAL_LM",
)

几个参数可以这样理解：

参数 含义
r=16 LoRA 低秩矩阵的秩，越大可训练能力越强，但参数更多
lora_alpha=32 LoRA 缩放系数，影响 Adapter 更新强度
target_modules="all-linear" 对模型中的线性层应用 LoRA
lora_dropout=0.05 训练时加入少量 dropout，降低过拟合风险
task_type="CAUSAL_LM" 基座模型仍按因果语言模型方式训练

直观理解：Gemma 4 的主体参数被冻结，LoRA 只训练外挂的小矩阵。这样既保留了基座模型能力，又能让模型快速适配情感分类任务。

3. 训练参数：每个设置都在权衡速度和稳定性
#

除了 LoRA 配置，训练参数同样会影响最终效果。一次典型的小规模实验可以关注这些配置：

参数 作用 实践理解
num_train_epochs=1 训练轮数 第一次先跑 1 轮，确认流程正确
per_device_train_batch_size=4 单卡 batch size 越大越吃显存，显存足够时可适当增大
gradient_checkpointing=True 梯度检查点 用计算换显存，适合大模型训练
bf16=True 使用 bfloat16 在支持 bf16 的 AMD GPU 上兼顾速度和稳定性
learning_rate 学习率 太大容易不稳定，太小收敛慢
logging_steps 日志间隔 方便观察 loss 变化
save_steps 保存间隔 避免训练中断后完全丢失结果

这些参数没有放之四海皆准的最优解。我的理解是：第一次实验的目标不是调到最好，而是选择一组保守参数，先确认整条链路能稳定完成。

4. 训练设置：先跑通一个最小闭环
#

本次训练只跑了 1 个 Epoch，大约 250 steps，耗时约 17 分钟。

我比较赞同这种“先小规模跑通”的方式。第一次微调时，目标不应该是立刻追求最优指标，而是先验证：

  1. 数据能否正常加载；
  2. Prompt 格式是否正确；
  3. 模型能否正常前向和反向传播；
  4. LoRA Adapter 是否能保存；
  5. 评估脚本是否能跑通；
  6. 微调后是否真的有提升。

只有这个闭环跑通后，继续增加 epoch、扩大数据集、调学习率和 batch size 才有意义。

5. 训练过程：Loss 曲线给出的反馈
#

训练过程中，Loss 从约 0.57 逐步下降到约 0.10。虽然单次实验不能只看 Loss 下结论，但它至少说明模型确实在学习训练样本中的规律。

更重要的是，Loss 下降需要和验证集指标一起看。如果训练 Loss 不断下降，但验证集准确率不升反降，就可能出现过拟合。

6. 评估结果：微调效果非常直观
#

本次实验中，微调前后的指标对比如下：

评估阶段 Accuracy Macro F1 Invalid Prediction
微调前 0.625 0.482 2
微调后 0.915 0.864 0

可以看到：

  • 准确率从 62.5% 提升到 91.5%；
  • Macro F1 从 0.482 提升到 0.864；
  • 无效预测从 2 降到 0；
  • 模型不仅分类更准，输出格式也更稳定。

其中 Invalid Prediction 是一个很有价值的指标。对于分类任务来说，模型输出的不是合法标签，就算语义上看起来“差不多”，程序也无法稳定解析。微调后无效预测归零，说明模型确实学会了按照固定标签空间回答。

指标小解释：为什么不只看 Accuracy？
#

Accuracy 是最直观的指标，但情感分类数据可能存在类别不均衡。例如 joy、sadness 样本很多，而 surprise、fear 样本较少。

这时只看准确率可能会掩盖模型在少数类上的问题。Macro F1 会分别计算每个类别的 F1，再做平均，因此更能反映模型对不同情绪类别的整体掌握程度。

简单理解：

  • Accuracy：整体答对了多少；
  • Macro F1：每一类情绪是否都学得比较均衡；
  • Invalid Prediction：输出是否符合可解析格式。

对于真正要部署到业务里的分类模型，这三个指标都值得关注。

评估代码思路
#

评估过程本质上是把验证集样本逐条送给模型，然后把模型输出解析成标签，再和真实标签比较。伪代码可以写成这样：

valid_labels = {"anger", "fear", "joy", "love", "sadness", "surprise"}

predictions = []
invalid = 0

for sample in eval_dataset:
    prompt = build_prompt(sample["text"])
    output = generate(model, tokenizer, prompt)
    pred = normalize_label(output)

    if pred not in valid_labels:
        invalid += 1
        pred = "invalid"

    predictions.append(pred)

然后用 scikit-learn 计算指标：

from sklearn.metrics import accuracy_score, f1_score, classification_report

acc = accuracy_score(y_true, y_pred)
macro_f1 = f1_score(y_true, y_pred, average="macro")
print("Accuracy:", acc)
print("Macro F1:", macro_f1)
print(classification_report(y_true, y_pred))

这里最关键的是 normalize_label()。模型输出可能带空格、换行或大小写差异，例如 Joy\n，需要先做清洗再比较：

def normalize_label(text):
    return text.strip().lower().split()[0]

对于分类任务来说，评估代码的鲁棒性很重要。否则模型明明输出了正确标签，却因为多了一个换行或标点被误判。

微调后的模型如何使用？
#

LoRA 微调完成后，通常会保存一个 Adapter 目录，而不是保存完整的基座模型。

使用时一般有两种方式：

方式一：基座模型 + Adapter 动态加载
#

适合开发调试和多任务切换。可以保留一个 Gemma 4 基座模型，然后根据任务加载不同 LoRA Adapter。

优点：

  • Adapter 文件小；
  • 多任务切换方便；
  • 不需要复制多份完整模型。

方式二：Merge 后导出完整模型
#

将 LoRA Adapter 合并回基座模型，得到一个独立的微调后模型。

优点：

  • 部署时加载逻辑更简单；
  • 不依赖额外 Adapter 路径；
  • 适合后续推理服务统一管理。

对于初学阶段，我更推荐先使用“基座模型 + Adapter”的方式。等任务稳定后，再考虑 merge 和部署优化。

常见问题与解决方案
#

问题 可能原因 解决方案
导入 transformers 报 torchaudio 错误 torchaudio 与 ROCm / PyTorch 版本不兼容 卸载 torchaudio，然后重启 Kernel
BloomPreTrainedModel 等模块找不到 transformers 大版本接口变化 使用兼容的 transformers 4.x 版本，不要盲目升级
数据集加载参数报错 ModelScope 与 datasets 版本不匹配 先下载 parquet 到本地，再用 datasets.load_dataset 加载
显存不足 batch、上下文长度或精度设置过高 降低 batch size、开启 gradient checkpointing、减少 max length
微调后输出一大段解释 Prompt 没有限制输出格式，训练样本格式不统一 在 system prompt 和 label 中明确只输出一个标签
训练 Loss 降低但验证效果差 过拟合或数据分布不一致 减少 epoch，检查训练/验证集划分，增加正则化
Adapter 加载后效果没变化 没有正确加载 LoRA 权重，或加载路径错误 打印模型结构，确认 PEFT Adapter 已挂载
评估结果波动较大 验证集样本太少或采样参数不稳定 固定随机种子，关闭随机采样，使用确定性解码

对比上一篇部署笔记：部署和微调的区别
#

上一篇笔记主要关注“如何让模型跑起来”，这篇则关注“如何让模型学会一个任务”。两者看起来都在操作大模型，但目标完全不同。

维度 部署 微调
核心目标 让模型提供推理服务 让模型适配特定任务
主要操作 下载权重、启动 vLLM、调用 API 准备数据、训练 Adapter、评估指标
资源重点 推理显存、吞吐、延迟 训练显存、梯度、优化器状态
成功标志 模型能返回回答 指标提升且输出格式稳定
常见问题 服务启动失败、端口连接失败 依赖冲突、显存不足、过拟合

把这两次实践连起来看，就形成了一条很完整的路径：

部署通用模型 → 理解推理服务 → 准备任务数据 → LoRA 微调 → 评估效果 → 再部署定制模型

这也是我觉得 Datawhale × AMD 这次活动设计比较好的地方：先让模型跑起来，再让模型为具体任务服务，学习曲线比较自然。

学习心得
#

1. 微调像是给模型一本“岗位手册”
#

预训练模型已经具备大量通用知识，但它不一定知道我们希望它如何回答。情感分类任务要求模型只输出固定标签，这就是一种很明确的“岗位规范”。

LoRA 微调的过程，就像给模型一本新员工手册：不需要重塑整个大脑，只需要让它学会某个场景下的工作方式。

2. 输出格式本身也是能力的一部分
#

微调前，模型可能会解释、扩写，甚至输出不在标签空间里的内容。对于聊天来说这也许没问题，但对于分类系统来说就是不可用。

微调后无效预测变成 0，让我意识到：微调不仅提升“答对率”，也能提升“可工程化程度”。

3. ROCm 生态已经能完成主流大模型训练任务
#

这次体验中，AMD GPU 在 PyTorch、bf16、LoRA 训练上整体表现不错。真正花时间的地方反而不是硬件性能，而是 Python 依赖和版本兼容。

这说明 ROCm 生态已经具备实战能力，但开发者仍然需要对依赖管理保持敏感。尤其是大模型训练工具链更新很快，版本组合是否稳定非常关键。

4. 先跑通小实验，再追求更高指标
#

第一次做微调时，不建议一上来就拉满数据量、epoch 和复杂超参。更稳的方式是：

  1. 先用少量数据跑通流程；
  2. 确认训练、保存、评估都正常；
  3. 再逐步扩大数据和训练轮数；
  4. 最后再做学习率、batch size、LoRA rank 等超参调优。

这样即使出错，也更容易定位问题。

下一步可以继续探索什么？
#

这次实验只是 LoRA 微调的入门版，后面还可以继续尝试：

方向 可以探索的问题
数据质量 清洗错误标签、平衡不同情绪类别、增加难例样本
Prompt 设计 不同 system prompt 是否影响分类稳定性
LoRA 超参 调整 r、lora_alpha、target_modules 对效果的影响
训练轮数 观察 epoch 增加后是否继续提升，还是开始过拟合
模型部署 将微调后的 Adapter 接入 vLLM 或其他推理服务
量化训练 在显存更小的环境中尝试 QLoRA
