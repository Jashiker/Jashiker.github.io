15 分钟在 AMD ROCm 云平台部署 Gemma 4
#

Datawhale × AMD 联合组队学习活动 Day 1-2 实践记录。

目标很简单：在 AMD ROCm 云 GPU 环境中下载 Gemma 4 模型，用 vLLM 启动推理服务，并通过命令行完成一次真实对话。

写在前面
#

作为一个对大模型充满好奇、但一直没找到合适上手机会的开发者，这次 Datawhale 和 AMD 联合推出的组队学习活动让我眼前一亮：活动提供了 AMD ROCm 云 GPU 环境，并配套了从模型下载到推理部署的完整教程。

整个过程不到 15 分钟，却让我第一次真正意义上把一个开源大模型从“模型文件”跑成了“可对话服务”。这篇文章记录我的完整实践过程、踩过的坑和一些学习心得，希望能帮到同样想入门大模型部署的朋友。

这篇笔记更偏向“第一次跑通”的实践记录，不会展开复杂的模型训练原理。读完以后，你应该能理解：

  • ROCm 云环境里应该先检查什么；
  • 模型权重下载到哪里；
  • vLLM 服务启动后到底提供了什么；
  • 为什么需要再开一个终端进行对话；
  • 遇到显存、依赖、连接问题时如何排查。

先搞懂：Gemma 4 是什么？
#

动手之前，我先简单了解了一下这次要运行的模型。知道自己跑的是什么，比机械复制命令更重要。

项目 说明
模型 Gemma 4
来源 Google DeepMind 发布的开源大模型家族
协议 Apache 2.0，可免费下载、修改和商用
版本 E2B、E4B、26B、31B 等规格
能力 文本理解、生成、代码辅助、多语言任务等
本文使用 google/gemma-4-E4B-it

本次教程使用的是 E4B 版本。它的参数规模适合单卡运行，部署门槛相对较低，也足够用于体验完整的大模型推理链路。

这里我比较关注的不是“模型榜单分数”，而是它是否适合作为入门部署对象。对第一次实践来说，一个合适的模型最好满足三个条件：

  1. 模型规模不要太大：否则容易被显存、下载时间和启动时间劝退。
  2. 生态支持比较完善：能被常见推理框架加载，遇到问题也更容易搜索到资料。
  3. 效果足够直观：部署完成后能通过对话立刻看到反馈，形成正向激励。

Gemma 4 E4B 版本刚好比较符合这些条件，因此很适合作为 ROCm + vLLM 的第一次实践目标。

高频概念速查
#

如果你和我一样刚开始接触大模型部署，下面几个概念很值得先理清楚。

概念 简单理解
参数 / 权重 模型“大脑”里的数字记忆，通常保存在 model.safetensors 等文件中
B Billion，10 亿。4B 大约表示 40 亿参数量级
推理 Inference 使用训练好的模型完成实际任务，比如回答问题、写代码、总结文本
部署 Deploy 把模型放到服务器或云环境中，让它可以被访问和调用
ModelScope 国内模型社区和下载平台，国内网络环境下下载模型更方便
vLLM 高效大模型推理框架，负责加载模型并提供 API / Chat 服务

一句话总结：

模型是一堆参数，推理是用这些参数计算结果，部署是让模型变成可访问的服务，而 vLLM 是让这个服务高效跑起来的推理引擎。

实战流程：四步跑通部署
#

整体链路如下：

检查 GPU → 下载模型 → 启动 vLLM 服务 → 新终端对话测试
   │           │             │                  │
   ▼           ▼             ▼                  ▼
 amd-smi   ModelScope   模型加载到显存      客户端发送请求
 确认硬件   国内加速下载    开启 API 服务      服务端返回回答

核心目标只有一个：把“网上的模型文件”变成“能和你对话的本地服务”。

第一步：确认云环境和 GPU 可用
#

登录 AMD 开发者平台，进入云环境后打开 Terminal，先确认 GPU 和 PyTorch 环境是否正常。

查看环境概览
# 

cat /etc/os-release
python --version
pip --version

AMD 云环境预装了 Ubuntu 和 Python，主要用来确认我们已有的基础环境，后面安装依赖时心里有数。

检查 GPU
# 

amd-smi

如果能看到 GPU 信息输出，说明显卡已经正常挂载。

确认 PyTorch 能识别 ROCm GPU
# 

python -c "import torch; print('PyTorch:', torch.__version__); print('ROCm available:', torch.cuda.is_available()); print('Device:', torch.cuda.get_device_name(0) if torch.cuda.is_available() else 'N/A')"

重点看这一项：

ROCm available: True

如果输出为 True，说明 PyTorch 已经可以通过 ROCm 使用 AMD GPU。

更详细的 GPU 状态可以用这个命令查看：

amd-smi monitor --perf

可以看到实时的显存占用、核心利用率、功耗等指标。建议启动 vLLM 后再开一个终端跑这个命令，观察模型加载和推理时的 GPU 资源变化——这对理解“推理为什么需要显存”很有帮助。

这一步虽然简单，但非常关键。它相当于开工前检查工具是否齐全。如果 GPU 没有被正确识别，后面下载模型、启动 vLLM 都可能白忙。

第二步：下载 Gemma 4 模型
#

国内环境下，直接从 Hugging Face 下载模型可能比较慢，所以这里使用 ModelScope。

在这一步需要区分两个概念：

  • pip 镜像源：用于加速 Python 包下载，例如 modelscope、vllm 等依赖。
  • ModelScope 模型仓库：用于下载模型权重，例如 model.safetensors、config.json、tokenizer 文件等。

也就是说，pip 解决“工具怎么装”，ModelScope 解决“模型从哪下”。

切换 pip 镜像源
# 

pip config set global.index-url https://mirrors.cloud.tencent.com/pypi/simple/

安装 ModelScope
# 

pip install modelscope

下载模型
# 

modelscope download --model google/gemma-4-E4B-it --cache_dir "./models"

下载大约需要几分钟，具体时间取决于网络和云环境状态。

注意：下载过程中进度条偶尔看起来像“卡住了”，这通常是正常现象。只要没有明确报错，可以耐心等待。

看到类似下面的信息，就说明模型下载完成：

Successfully Downloaded from model google/gemma-4-E4B-it

检查模型文件
# 

ls -lh ./models/google/gemma-4-E4B-it/

如果能看到较大的 model.safetensors 文件，就说明模型权重已经下载到本地。这个文件就是模型的“本体”。

一般模型目录里会包含几类文件：

文件 作用
config.json 模型结构配置，例如层数、隐藏维度、上下文长度等
model.safetensors 模型权重文件，也就是主要参数所在位置
tokenizer.json / tokenizer 相关文件 分词器配置，用于把文本转换成模型能理解的 token
generation_config.json 生成相关默认配置，例如采样参数等

这也解释了为什么“下载模型”不是只下载一个文件。大模型推理需要结构配置、权重和分词器一起配合，缺任何一部分都可能导致加载失败。

这一阶段我最大的体会是：选对下载渠道很重要。ModelScope 和国内 pip 镜像能省掉大量网络问题，把精力留给真正的部署和理解。

第三步：启动 vLLM 推理服务
#

云环境中可能需要更新 vLLM 相关依赖。教程中使用的是 ROCm wheel 源。

uv pip uninstall torchvision
uv pip install vllm torchvision \
  --no-cache \
  --index-url https://mirrors.aliyun.com/pypi/simple/ \
  --extra-index-url https://wheels.vllm.ai/rocm/ \
  -U

这里有几个参数值得单独解释一下：

参数 作用
uv pip uninstall torchvision 先卸载可能不匹配的 torchvision，避免和 ROCm 版本依赖冲突
--no-cache 不使用本地缓存，避免拿到旧 wheel
--index-url 指定主要 Python 包下载源
--extra-index-url 额外指定 vLLM ROCm wheel 源
-U 升级到可用的新版本

ROCm 场景下，依赖版本匹配比普通 Python 项目更敏感。尤其是 PyTorch、torchvision、vLLM、ROCm runtime 之间需要相互兼容，否则可能出现安装成功但运行失败的情况。

然后启动模型服务：

vllm serve ./models/google/gemma-4-E4B-it/ \
  --served-model-name gemma-4-E4B-it

运行后，这个终端窗口会被 vLLM 服务占用。不要关闭，也不要按 Ctrl+C，否则服务会停止。

第一次启动时，vLLM 需要加载模型、分配显存，并可能进行内核编译。只要日志还在持续输出，就不用着急。

vLLM 启动时的日志怎么看？
#

这是 vLLM 服务成功启动后比较常见的输出内容（简化示意）：

INFO 06-12 10:00:00 engine.py:100] Initializing an LLM engine with config:
      model=./models/google/gemma-4-E4B-it/, tensor_parallel_size=1, dtype=auto
INFO 06-12 10:00:05 model_runner.py:200] Loading model weights took 3.8 GB
INFO 06-12 10:00:10 worker.py:150] GPU memory usage: 4.2 GB allocated, 3.1 GB free
INFO 06-12 10:00:15 launcher.py:250] Available routes are:
      GET /health
      POST /v1/chat/completions
      POST /v1/completions
      GET /v1/models
INFO 06-12 10:00:15 server.py:80] Application startup complete.
INFO 06-12 10:00:15 server.py:85] Uvicorn running on http://0.0.0.0:8000

几个关键行：

日志行 说明
Loading model weights took 3.8 GB 模型权重加载到显存，这是推理的“启动成本”
GPU memory usage: 4.2 GB allocated 已分配的显存，包括了 KV Cache 等预留空间
Available routes are ... API 端点已经注册，说明 HTTP 服务可用
Application startup complete 服务就绪，可以开始对话测试

如果你看到 Application startup complete，就可以准备进入第四步了。

第四步：新终端进行对话测试
#

这里有一个很重要的概念：服务端 + 客户端模式。

  • 第一个终端：服务端，负责加载模型并持续提供 API 服务。
  • 第二个终端：客户端，负责向服务端发送请求并接收回答。

保持第一个终端运行，重新打开一个终端，输入：

vllm chat --url http://localhost:8000/v1 --model gemma-4-E4B-it

然后发送测试消息：

你是谁，你能做什么？

当终端返回 Gemma 4 的回答时，就说明部署成功了。

除了 vllm chat，还可以用 OpenAI 兼容接口直接测试 HTTP API：

curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gemma-4-E4B-it",
    "messages": [
      {"role": "user", "content": "用三句话解释什么是 ROCm"}
    ],
    "temperature": 0.7,
    "max_tokens": 256
  }'

如果能返回 JSON 格式的模型回答，说明 vLLM 不只是能在命令行聊天，还已经提供了标准的 API 服务。后续无论是接入 Web 应用、脚本，还是其他 Agent 框架，本质上都可以通过这个接口完成。

我当时的感受是：这 15 分钟非常值得。从一个“挂在网上的模型文件”，到一个“能和我对话的服务”，这种从无到有的成就感，是单纯看论文和教程很难获得的。

实验效果记录
#

模型成功响应用户查询
#

图 1：Gemma 4 成功回答“你是谁，你能做什么？”的问题。

从回答内容看，模型能够介绍自身能力，例如：

  • 回答问题
  • 生成文本
  • 翻译内容
  • 总结和提炼信息
  • 辅助代码编写
  • 进行头脑风暴
  • 支持连续对话交流

同时，模型也会说明自身局限性，例如知识时效、事实核查不确定性，以及不能直接执行现实世界操作等。

vLLM 服务端日志正常
#

图 2：vLLM 服务启动成功，API 端点正常。

从服务端日志可以看到几个关键信号：

  • Application startup complete：服务启动完成。
  • Available routes are ...：API 路由已经注册。
  • http://0.0.0.0:8000：服务正在监听 8000 端口。
  • 吞吐指标正常输出：说明请求正在被模型处理。

第一次启动时可能会看到类似 Triton kernel JIT compilation during inference 的 warning。这通常是首次运行时的编译过程，后续请求会更快。

资源占用与性能观察
#

部署大模型时，最容易被忽略的其实是资源观察。模型能不能跑起来，不只取决于命令是否正确，还取决于显存、上下文长度、batch 大小和推理框架的调度方式。

可以在服务端运行时打开另一个终端，观察 GPU 状态：

watch -n 1 amd-smi

重点关注几项：

指标 观察重点
显存占用 模型加载后显存会明显上升，这是正常现象
GPU 利用率 用户请求进入时利用率会上升，空闲时可能较低
温度 / 功耗 云环境一般已经做好散热和功耗限制，主要用于了解运行状态
进程信息 可以确认当前 GPU 是否被 vLLM 进程占用

如果显存压力比较大，可以从这几个方向排查：

  1. 降低上下文长度，例如添加 --max-model-len 8192 或 4096。
  2. 确认没有重复启动多个 vLLM 服务。
  3. 关闭不必要的 Python 进程或 notebook kernel。
  4. 优先选择参数规模更小的模型做第一次实验。

这里我也更直观地理解了一个概念：大模型部署不是“把文件放上去”这么简单，而是要把模型权重、运行时缓存、请求上下文一起放进 GPU 显存里。显存是推理服务最核心的资源之一。

为什么 vLLM 适合做推理服务？
#

传统理解里，模型推理似乎只是“输入一句话，模型输出一句话”。但真正部署成服务后，会遇到很多工程问题：

  • 多个请求同时进来如何排队；
  • 长文本上下文如何管理显存；
  • token 生成过程如何提高吞吐；
  • 模型服务如何暴露成标准 API；
  • 如何兼容 OpenAI 风格的调用方式。

vLLM 的价值就在这里。它不只是一个“加载模型的工具”，更像是一个面向大模型推理的服务引擎。对初学者来说，最直接的好处是：只要模型能被 vLLM 正确加载，就可以很快得到一个可访问的 HTTP API。

这也是为什么本次实践中，vllm serve 是从“模型文件”到“可对话服务”的关键一步。

常见问题与解决方案
#

问题 可能原因 解决方案
vllm serve 启动很慢 第一次需要加载模型和编译内核 等待几分钟，只要日志还在输出就不要中断
提示显存不足 默认上下文长度过大或显存不足 尝试添加 --max-model-len 8192，不行再降到 4096
modelscope 命令找不到 ModelScope 没有安装或环境不一致 先执行 pip show modelscope，没有就重新 pip install -U modelscope
聊天命令连接失败 vLLM 服务端没有运行或尚未启动完成 确认第一个终端仍在运行，并出现 Application startup complete
下载速度慢 网络或源不稳定 使用 ModelScope，并切换到国内 pip 镜像源
API 返回模型不存在 --served-model-name 和请求里的 model 不一致 保持二者一致，例如都使用 gemma-4-E4B-it
端口被占用 8000 端口已有其他服务 更换端口，例如 --port 8001，客户端也同步修改 URL
启动后第一次回答很慢 首次请求触发编译或缓存初始化 等待第一次请求完成，后续通常会更快

命令速查
#

为了方便复盘，这里把本次用到的核心命令整理成一份最小清单。

# 1. 检查 GPU
amd-smi

# 2. 检查 PyTorch / ROCm
python -c "import torch; print(torch.__version__); print(torch.cuda.is_available()); print(torch.cuda.get_device_name(0) if torch.cuda.is_available() else 'N/A')"

# 3. 配置 pip 镜像
pip config set global.index-url https://mirrors.cloud.tencent.com/pypi/simple/

# 4. 安装 ModelScope
pip install modelscope

# 5. 下载模型
modelscope download --model google/gemma-4-E4B-it --cache_dir "./models"

# 6. 安装 / 更新 vLLM ROCm 版本
uv pip uninstall torchvision
uv pip install vllm torchvision \
  --no-cache \
  --index-url https://mirrors.aliyun.com/pypi/simple/ \
  --extra-index-url https://wheels.vllm.ai/rocm/ \
  -U

# 7. 启动服务
vllm serve ./models/google/gemma-4-E4B-it/ \
  --served-model-name gemma-4-E4B-it

# 8. 新终端聊天测试
vllm chat --url http://localhost:8000/v1 --model gemma-4-E4B-it

如果只想快速复现，可以按照这份命令清单从上到下执行；如果遇到问题，再回到前面的分步说明中看原因和排查方式。

学习心得
#

1. 先跑通，再深入理解
#

作为非 AI 科班出身的开发者，我之前习惯先啃理论再动手。但这次实践让我意识到：在大模型领域，先跑通一个最小闭环，再回头理解原理，效率会更高。

当我真正看到模型在终端里回复内容后，反而更有动力去理解 Transformer、注意力机制、推理框架和显存管理这些底层知识。

2. 开源生态降低了大模型入门门槛
#

开源模型、模型社区、推理框架和云 GPU 环境组合在一起，让普通开发者也可以低门槛完成一次大模型部署。过去看起来很遥远的事情，现在可以被拆成几条命令一步步完成。

3. ROCm 生态正在变得更易用
#

我之前一直觉得 AMD GPU 跑大模型的生态会比 CUDA 麻烦很多。但这次体验下来，ROCm 云环境开箱即用，PyTorch 能识别 GPU，vLLM 也可以顺利启动服务。

这说明 ROCm 在 AI 开发场景中的可用性正在快速提升，也给开发者提供了 CUDA 之外的另一种选择。

4. 理解服务端和客户端架构很重要
#

教程里“开新终端对话”的设计看似麻烦，其实是在模拟大模型服务的真实使用方式：

  • 服务端持续运行模型。
  • 客户端通过 API 发送请求。
  • 模型处理请求后返回结果。

以后无论是调用本地模型、云端模型，还是接入 OpenAI / Claude / 通义 / DeepSeek 等 API，本质上都离不开这个模式。

下一步：从部署走向定制
#

部署只是起点。这个活动后续的教程还会介绍：

  1. 使用自己的数据微调 Gemma 4，让模型具备更贴近特定任务或领域的能力。
  2. 微调时机和场景判断：什么情况下直接 Prompt 就够，什么情况下需要微调。
  3. 评估微调后的效果：在特定任务上对比微调前后的表现差异。

也借这次机会记录一下自己下一步想要更深入了解的几个方向：

方向 为什么感兴趣
vLLM 的 PagedAttention 机制 显存管理是大模型部署的核心，理解它有助于部署更大模型
微调的技术栈 LoRA / QLoRA 的原理，以及在 ROCm 上的实践方式
推理优化 量化（INT4 / INT8）、KV Cache、continuous batching 等提升吞吐的技术
ROCm vs CUDA 的生态对比 不同场景下的工具链支持程度和部署成本差异

总结
#

这次实践可以浓缩成一句话：

用 AMD ROCm 云 GPU + ModelScope + vLLM，把 Gemma 4 从模型文件部署成一个可对话的大模型服务。

整个过程最有价值的地方，不只是跑通了几条命令，而是建立了一个完整的认知闭环：

  1. GPU 环境是否可用；
  2. 模型权重如何下载；
  3. 推理服务如何启动；
  4. 客户端如何调用模型；
  5. 如何观察资源占用；
  6. 出错时应该从哪里排查。

如果把这次实践抽象成一套通用方法，其实不只适用于 Gemma 4，也适用于很多其他开源大模型：

选模型 → 准备运行环境 → 下载权重 → 选择推理框架 → 启动服务 → API 调用 → 观察和调优

第一次跑通以后，再切换模型、调整参数、接入应用，就不再是完全陌生的事情了。

感谢 Datawhale 和 AMD 提供这次免费的学习资源和云 GPU 算力。对于想入门大模型部署的开发者来说，这样的实战任务非常适合作为第一步。
